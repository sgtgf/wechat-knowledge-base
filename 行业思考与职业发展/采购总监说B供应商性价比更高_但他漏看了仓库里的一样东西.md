# 采购总监说B供应商性价比更高，但他漏看了仓库里的一样东西

原创 傅存敬 电磁散人 2026-05-17 07:06 广东

> 原文地址: [https://mp.weixin.qq.com/s/DCZjvfdmLfLay1rSO7kozQ](https://mp.weixin.qq.com/s/DCZjvfdmLfLay1rSO7kozQ)

各位同仁，前阵子我经历了一件小事，讲出来大家多半都有共鸣。

一个欧洲电动工具品牌客户启动了新平台项目，RFQ 发过来，附件一打开，技术规格书后面压着两份长长的表格。一份是 Supplier Self-Assessment Questionnaire，供应商自评问卷；另一份是 Component-Level Cost Breakdown Template，零部件级成本拆解模板。

我坐下来填。

问卷部分先来。公司成立年份、注册资本、厂房面积、员工总数、IATF 16949 证书编号及有效期、ISO 14001、UL 认证清单、RoHS/REACH 符合性声明。再往下是设备清单：绕线机数量、SMT 产线条数、回流焊型号、AOI 设备品牌、动平衡机精度等级。再往下是质量数据：过去十二个月客户 PPM、来料 IQC 合格率、关键工序 CPK 值、8D 报告平均关闭周期。最后还有一页财务和知识产权：年营收、净利率、资产负债率、发明专利数。

每一栏都有明确的数字或证书号往里填，很顺手。

然后是成本拆解那张表。永磁体：牌号、克重、供应商、单价。硅钢片：牌号、片厚、用量、单价。漆包线、MOSFET、MCU、PCB、轴承、机壳、注塑件、紧固件、包装材料……每一行都是"规格 / 用量 / 供应商 / 单价 / 小计"五栏，填完之后整张表的 Bottom Line 是一个干干净净的美元数字。

我填到最后一栏，停了下来。

说不上来哪里不对劲，但就是觉得不对劲。表填得越完整，这种感觉越明显。

我们公司有一个团队，十多个人。他们做的事，在这两张表里没有任何一行可以对应。

他们调 PI 参数。他们写状态机。他们花两个礼拜定位一个只在零下二十度冷启动时偶发的相电流毛刺。他们为了让电机在堵转瞬间不"哼"出那个让用户皱眉的频率，反反复复改了十一版 PWM 调制策略。工位上堆着示波器、电流钳、热成像仪，硬盘里躺着上百个 .mat 文件和 .slx 模型，每个文件名背后都是一次彻夜的整定。

这十几个人的两年时间——让这台电机真正"会做事"的那一部分——在客户的评估表里，没有一栏可以填。

MCU 型号那一栏可以填，但 MCU 里跑着什么代码不能填。研发人员总数那一栏可以填，但其中几个人能真正把 FOC 调到极限，写不进去。专利数可以填，但代码仓库里那些没申请专利、只是默默工作着的工程经验，也写不进去。

我把表合上，泡了杯茶。客户的采购总监此刻多半正在另一间会议室里，对着十几份这样填好的表做横向对比。他会看到一切能被看到的东西，然后用这些东西做出一个决定。

而那个决定，将悄悄影响一个他从未在表上见过的东西的命运——那十几个工程师明年还在不在这家公司，明年还有没有时间把那十一版调制策略改到第十二版。

这不是某一家客户的问题。

各位同仁不妨做一个思想实验：把我们这个行业里你能想到的评估工具全部摆在桌面上，然后找一找，哪一个给软件留了真正的位置？

客户的 RFQ 模板我刚才填过了，结论不用多说。

那咨询公司的供应商评估报告呢？麦肯锡也好、罗兰贝格也好，给终端品牌做供应链战略的分析框架都是那一套：材料成本、制造成本、品质成本、物流成本、管理费用加利润。软件在哪里？在"研发费用摊销"那个百分比里，跟厂房折旧、行政人员工资挤在一起。说白了，一个调了两年的无感 FOC 算法，和一个门卫大爷的社保公积金，在报告里享受同一栏待遇。

上市公司年报呢？翻一翻几家电机上市公司的年报，主要原材料永远是那几位老面孔：稀土永磁材料、硅钢片、漆包线、轴承，加起来占营业成本的六七成。剩下三四成笼统叫"其他"。软件工程师的工资、Simulink 的 License、JTAG 调试器的损耗——全在"其他"里。投资者读完年报，会觉得这家公司的核心竞争力是"稀土采购能力"。你跟他说"不对，是算法调试能力"，他看着年报上的数字，多半觉得你在说段子。

IATF 16949 的过程审核呢？VDA 6.3 倒是有一章叫"产品和过程开发"，里面会问软件开发流程——ASPICE 等级、需求追溯矩阵、版本管理。但问的是"你有没有这个流程"，不是"你的代码好不好"。一个流程齐全但算法平庸的供应商，和一个流程粗糙但代码精湛的供应商，在审核打分上完全可能倒挂。审核员也没办法，你让他读 C 代码判断 FOC 实现质量？这不是他的专业。

行业协会发布的 Should-Cost Model 就更不用说了。那类模型的基本假设是"成本等于材料加工时加制造费用分摊"，颗粒度可以细到每一道工序的节拍时间和设备折旧率，但在"控制器"这一项上通常只有一行：MCU + MOSFET + 驱动 IC + 无源器件 + PCB + SMT 加工费。代码不占物理空间，不消耗原材料，不需要设备加工——所以在这个模型的世界观里，代码的成本就是零。

这些工具一字排开，你会发现一件事——它们的格子各不相同，但它们共同少了的那一行，是同一行。

为什么会这样？我琢磨了挺久。

最直接的原因，是制造业几十年来所有的成本核算和价值评估，都长在同一棵树上——BOM，物料清单。这是制造业的母语。BOM 定义了什么东西"算"成本：有料号的算，有供应商编码的算，有入库单的算，能过磅称重的算。后面所有的分析工具——TCO 模型、价值工程、Should-Cost、供应商评分卡——都是从 BOM 这棵树干上长出来的枝叶。

这棵树长了几十年，长得很好，问题在于它的根扎在一个前提里：**成本的载体是物质**。

在这个前提下，一颗 MCU 有成本，因为它是一颗芯片，可以采购、入库、贴片、称重。但 MCU 里跑的代码不是物质。它没有重量、没有体积、不需要仓储、不占运输空间。从一个工程师的硬盘复制到一千块板子上，边际成本约等于烧录器通电的那零点几秒钟。所以在 BOM 的世界观里，代码不是"被低估了"——而是比这更糟——**它连被低估的资格都没有，因为 BOM 的格子里根本没有它的位置**。

各位同仁可以回想一下自己公司的 ERP 系统。原材料有料号，半成品有料号，成品有料号。你们的电机控制算法——有料号吗？

没有。那就完了。没有料号就进不了采购单，进不了采购单就进不了成本核算，进不了成本核算就没法出现在报价单上，也就不会出现在客户的评估表里，更不会出现在采购总监的决策依据里。这条路从头到尾走下来，软件被排除得干干净净。不是谁故意的，是路本身就没修到那个方向。

还有一层更深的原因。磁钢我知道它值多少钱——查牌号、查克重、查稀土现货价，乘一下就出来了。MOSFET 我也知道——立创商城上挂着呢。磁钢按克卖，铜线按米卖，MCU 按颗卖，每一样东西都有计量单位，有了计量单位就有了价格锚点，就可以做比较。

但一套 FOC 算法值多少钱？按行数算？一千行写得好的可能比一万行写得差的值钱十倍。按开发时间？一个高手三个月调出来的参数表，可能比三个新手花两年堆出来的更好。按功能名称？"无感 FOC"这几个字，背后可能是教科书级别的实现，也可能是勉强跑起来的拼凑。

没有计量单位的东西，不能标准化定价。不能定价的东西，写不进成本模型。写不进模型的东西，进不了报告。

《孟子》里有句话，"明察秋毫之末，而不见舆薪"。能看清秋天鸟兽新长的绒毛尖端，却看不见眼前一整车柴火。我们的评估体系就是这么一回事——磁瓦的牌号差异看得清清楚楚，MOSFET 的 Rds(on) 差了几个毫欧也逃不过去，但一整个代码仓库摆在那里，视而不见。不是眼神不好，是这只眼睛的构造决定了它能看什么、不能看什么。BOM 就是那只眼睛。

看不见会怎样？各位同仁可能觉得，看不见就看不见吧，行业转了这么多年也没塌。

但仔细想想，有些事情其实已经在发生了，只是它们也跟软件一样——不容易被看见。

回到开头那个场景。采购总监面前摆着十几份评估表，A 供应商报价 40 美金，B 供应商报价 20 美金。BOM 比对下来，B 的磁钢牌号稍低一点、MOSFET 换了国产替代、MCU 降了一档，这些差异大概能解释 8 到 10 美金。那剩下的 10 到 12 美金差在哪里？评估表上找不到答案。所以采购总监只能用他能看到的东西来解释——"A 供应商利润率太高"，或者"A 供应商管理效率有问题"。

但真实的答案可能是：A 供应商有五个工程师花了两年时间把控制算法调到极限——低速平稳、高速弱磁、堵转保护、温度补偿、噪音抑制——这些能力凝固在代码里，沉淀在参数表里。B 供应商用芯片厂的参考设计改了改，开发周期三个月，代码是现成的，报价里确实没有这笔成本——因为他确实没花这笔成本。两份报告摆在一起，B 看起来"性价比更高"。你不能说采购总监判断错了，他是在他能看到的信息范围内做了合理推断。问题出在那个"能看到的范围"本身。

然后就是连锁反应。当整个行业都按 BOM 打分、按硬件成本比价，供应商会怎么做？往评估表看得见的地方使劲呗。磁钢牌号客户盯着呢，不能动。MOSFET 品牌客户查得到，不能换。CPK 数据审核要看，得保持。那软件呢？评估表上没有那一栏，客户也不会专门来查代码——那就省省吧。六个月的算法调试期压成三个月，专职的嵌入式工程师换成校招生带着干，自研的 FOC 代码换成芯片厂 SDK。反正从评估表上看不出任何区别。

我不觉得这是谁的道德问题。**你考核什么，别人就优化什么——你不考核的，自然就被优化掉了**。这道理搞管理的都懂，但很少有人把它套到"软件在供应链评估中的地位"这件事上来想。

再往下想一步。TI 的 MCF8316A、英飞凌的 iMOTION、峰岹的 FU6866——这类 Codefree 芯片这几年越来越多。它们把控制算法固化在芯片里，用户不需要写代码，通过 GUI 配几个参数就能转。从芯片厂的角度这当然是好事，降低了开发门槛。但从产业链的角度看——如果算法本来就不在报价单上、不在评估表里、采购总监也从来没为它付过钱，那一颗"帮你省掉算法开发"的芯片，在客户眼里省掉的是什么？是一个本来就不存在的成本。客户不会因为你用了这颗芯片就觉得亏了，他只会觉得"本来就该这么便宜"。结果呢？更多没有算法能力的小厂能进场了，报价竞争更激烈了，利润空间更薄了。薄掉的那一层，恰好是算法投入。

最后一件事。前线的同仁可能已经注意到了——最近几年，终端品牌客户的投诉有一类变得越来越多：电机噪音比上一代大了一点点，堵转保护偶尔误触发，低速启动不够平滑，电池续航比竞品短了百分之几。用户在电商平台写"用起来总觉得差点意思"。

品牌客户的产品经理拿到投诉，打开供应商评估报告一看——BOM 没变、CPK 达标、认证齐全，一切正常。但用户说"差点意思"。这种报告上解释不了的落差，根因往往不在硬件。PI 参数没有针对新磁路充分整定，弱磁切换点设得不够精准，电流环带宽和机械共振频率撞到了一起——这些事情全在代码里，全在报告的盲区里。报告说正常，用户说不行。**谁对了？都对了。只不过他们在看不同的东西**。

讲了这么多"看不见"，可能有同仁要问：行业里的操盘手，有什么办法能多看到一点？

我没有什么体系化的方法论可以给——如果有，那它早就被写进评估表了。我只有这两年在实际工作中摸索出来的几个笨办法，不一定全面，但每一条都不在任何标准评估表里。

第一个，看版本历史。如果供应商愿意配合，请他打开代码仓库的 comit 记录给你看一看。不需要看代码内容，看提交频率、分支数量、最近一次版本更新是什么时候。一个活跃的仓库意味着算法还在被持续打磨；半年没有新 commit，要么是已经足够好了不用改，要么是已经没人管了。这两种情况差别很大，追问一句就知道。

第二个，看参数文档里有没有"为什么"。请供应商提供电机控制参数表，不是看 Kp 等于多少、Ki 等于多少——这些数字脱离工况没有意义。看的是每个参数旁边有没有注释。比如电流环 Kp = 0.8，旁边写着"基于 2kHz 带宽目标，考虑采样延迟一拍补偿和死区时间影响"——这说明这个参数是被真正理解了的。如果参数表只有一列数字，干干净净什么都不写，大概率是从参考设计抄过来的，或者是试错碰出来的。我有个偏激的说法：只有数值没有理由的参数表，等于没有软件。

第三个，看异常处理代码的密度。一套电机控制软件，"正常跑"的代码其实只占百分之三四十。剩下的全在处理各种不正常的情况——过流、过压、欠压、过温、缺相、堵转、失步、传感器挂了、通信超时、EMI 把 ADC 采样值弹飞了。请供应商画一张状态机迁移图，数一数有多少个状态、多少条迁移路径。一张只有"启动—运行—停止"三个圈的图，和一张密密麻麻十几个状态、几十条线的图，背后的工程投入根本不是一个量级。这个东西藏不了假，画出来一眼就知道。

第四个，问一个具体的问题。"你们的控制软件做过多少种工况组合下的参数扫描？"只在常温额定负载下跑过一遍的，和在零下二十度到零上八十五度、空载到堵转、最低电压到最高电压全矩阵扫过的——这是两种完全不同的软件。测试矩阵的规模，大概是我能想到的对软件投入最诚实的度量。

第五个，可能是最不像"评估指标"的一条，但我觉得反而最准。去了解一下过去一年里，客户的应用工程师给这家供应商打过几次技术支持电话，每次是什么事，怎么解决的，改的是代码还是参数还是硬件。一家供应商的软件到底厚不厚，不是写在文档里的——**是被客户的求助电话一遍一遍冲刷出来的**。求助少、解决快，说明大多数问题出厂前就被代码兜住了。反复出同类问题，说明那些异常路径根本没覆盖到。

这五条都不在 BOM 上，也不在任何标准评分卡里。但它们在工程师的硬盘上、代码仓库里、测试记录里、邮件存档里。愿意看的话，软件是能被看见的。只是要多走几步。

上一篇《[当芯片厂把算法做进硅片，我们该往哪里走](https://mp.weixin.qq.com/s?__biz=MzE5MTYzNjgzOA==&mid=2247486382&idx=1&sn=3c7c32814e3a668c84d6d7ad4bcb57fa&scene=21#wechat_redirect)》发出来之后，有位同仁问了个问题："报价单上看不到软件，那我们做深度调研、写详细的评估报告，能不能把软件找回来？"

这一篇算是我对那个问题的回答。

我的结论有点让人丧气——光靠现有的那套工具，找不回来。不是我们报告写得不够好、调研做得不够深。是那整套工具看世界的方式就是那样的。从 BOM 到 Should-Cost Model，从供应商评分卡到过程审核清单，它们用的是同一只眼睛。这只眼睛看得见一切有料号、有克重、有单价的东西。代码没有料号，所以它看不见。

我们这些年一直在升级工具——更细的成本模型、更全的审核清单、更聪明的分析引擎。看到的细节确实越来越多了，磁瓦的牌号差异看得更清楚了，MOSFET 的批次一致性看得更清楚了。但说到底，这些升级都是在同一个方向上看得更深，而不是转头看一看另一个方向。

老子说"大象无形"。软件就是我们这个行业里那头大象。它无形、无重、无料号，所以在所有以"形"为基础的评估体系里都是隐身的。但各位同仁心里清楚——它决定了这台电机是安静还是吵闹、是聪明还是笨拙、是让人放心还是让人提心吊胆。

这一篇和上一篇是姊妹篇。上一篇拆的是报价单那堵墙的一面，这一篇撞上了它的另一面。到这里各位大概已经明白了——它们是同一堵墙。一面写着"成本"，一面写着"评估"，遮住的东西是一样的：那些无法被物料清单表达的工程师智慧。

什么时候这堵墙能拆掉，我真说不好。但至少可以做一件小事——下次填评估表的时候，在那个 Bottom Line 旁边，手写一行备注。

写什么呢？

就写：此价格不含软件。
