## 一、案例回顾：“我的辨识怎么总被打断？”

算法工程师小林写了一套非常漂亮的电感辨识程序。它的逻辑是：先注入一个直流偏置，稳定200ms；然后叠加高频正弦波，采样500ms；最后停止注入，计算结果。整个过程大概需要1秒。

他把这段代码放到了主循环的一个`if`语句里，通过一个全局标志位`start_L_identification`来触发。

测试时，怪事发生了：

1.  **结果不稳定**: 同样一次触发，有时辨识出的电感是1.2mH，有时是0.8mH，还有时干脆是个负数。
    
2.  **辨识过程总被“打断”**: 他用示波器观察注入的电流波形，发现高频正弦波刚注入了100ms，就突然没了，过了一会儿又重新开始注入。整个过程断断续续，根本无法完成一个完整的采样周期。
    

小林百思不得其解，他的算法逻辑明明是对的，为什么执行起来就“七零八落”？

**问题出在哪里？**

问题出在他用了一个简单的`if`和全局标志位来管理一个**有时间顺序、有多个步骤**的复杂任务。在主循环里，任何其他的事件（比如一个故障保护、一个上位机指令、甚至是另一个辨识任务的误触发）都可能在`start_L_identification`为`true`的期间，干扰或重置他的辨识流程。

他设计的辨识流程，就像一首需要按节拍演奏的乐曲，但他的执行方式，却像是在一个嘈杂的菜市场里，随时可能被人打断、被人抢走乐器。

**问题的解决方案在哪儿？**

就在代码A中的`pm_fsm.c里的``**pm_FSM()**`函数。这个函数本身没有复杂的算法，但它提供了代码A的“**灵魂**”——一个**有限状态机 (Finite State Machine, FSM)**。它就是那个指挥家，确保无论是标定、辨识还是正常运行，每一个“乐章”都能在正确的时间、按正确的顺序、不受干扰地演奏。

今天，我们就来深入这个“指挥部”，看看状态机是如何把混乱的“并行请求”变成有序的“串行执行”，并为我们后续逐行讲解每个辨识`state`打下坚实的基础。

## 二、为什么需要状态机？——从“一锅粥”到“流水线”

在讲代码之前，我们先用一个生活比喻来理解为什么需要FSM。

想象一下做一道复杂的菜，比如“佛跳墙”，需要很多步骤：泡发海参、炖煮高汤、处理鲍鱼...

-   **没有FSM（全局变量+if-else）**: 你可能会用几个全局标志位：`is_haishen_paofa_done = false; is_gaotang_dunhao = false;`...然后在厨房的主循环里写一堆`if`：
    

```
if (!is_haishen_paofa_done) { 泡发海参(); }
```

这种写法，如果中间你妈让你去买瓶酱油（一个外部中断），或者你突然想起来还得处理一下冰箱里的剩菜（另一个任务），整个做菜流程就乱了。你回来的时候可能都忘了刚才做到哪一步，或者高汤还没炖好就去处理鲍鱼了。这就是“**一锅粥**”模式。

-   **有FSM（状态机）:****你会定义几个状态：**`**STATE_PAOFA_HAISHEN**`**,**`**STATE_DUN_GAOTANG**`**,**`**STATE_CHULI_BAOYU**`**...**
    

然后有一个“总管”（FSM函数），他只关心两件事：**当前状态是什么？**和**当前状态完成了没有？**

```
switch (current_state) {
```

这种方式，无论中间有多少干扰，总管始终记得“我们现在正在炖高汤”，并且只有在“高汤炖好了”这个条件满足时，才会进入下一步。这就是“**流水线**”模式，清晰、健壮、可预测。

### 3\. 深入微观：时间切片与相位计数器（以零漂校准为例）

我们要校准电流传感器的零点，通常需要采集几千次数据取平均。在中断里怎么写？写个`for(i=0; i<1000; i++)`？

**绝对不行！**那样中断就卡死了，看门狗会叫，电机也会失控。

看看这段代码是怎么写的（在`pm_fsm.c`中）：

```
static void pm_fsm_state_zero_drift(pmc_t *pm)
```

**精彩点 B：非阻塞式长任务设计**

-   **原理**：利用 `switch (fsm_phase)` 把一个长任务切成了很多片。
    
-   **Phase 0**：初始化。只跑一次。
    
-   **Phase 1**：**积攒数据**。这是最妙的。它利用了 FOC 本身的周期性中断。每次中断进来，它只做**一行代码**的事（采集一个点），然后马上退出。经过几千次中断（几百毫秒）后，数据攒够了，才自动跳到 Phase 2。
    
-   **效果**：虽然校准过程持续了 100ms，但每次中断的 CPU 占用率极低，完全不影响电机控制的实时性。这就是**时间切片（Time Slicing）** 的思想。
    

### 4\. 隐藏的数学家：最小二乘法（LSE）

有同仁可能注意到了代码里反复出现的`lse_t`，`lse_insert`，`lse_solve。`

**精彩点 C：在线参数辨识**

-   **背景**：一般的 FOC 代码，求平均值就用个累加器除以 N。但这份代码用的是 **LSE（Least Squares Estimator，最小二乘法估计器）**。
    
-   **为什么？**
    

-   在 `ZERO_DRIFT` 里，它不仅能算平均值（零偏），还能算出**方差**！
    
-   代码里有 `pm->self_STDi`。如果算出来的方差太大，说明现在的电流噪声太大，或者硬件坏了，直接报错 `PM_ERROR_LOW_CURRENT_ACCURACY`。
    
-   在 `PROBE_CONST_RESISTANCE`（测电阻）里，它利用 R = U/I 的线性关系，通过 LSE 拟合直线，直接算出电阻 。
    

-   **意义**：这让电机控制器具有了**自诊断**和**自学习**的能力。它不再是一个傻执行的驱控，而是一个能评估自己硬件健康状况、能自己测量电机参数的智能系统。
    

### 5\. 自检流程的艺术

这一块，绝对值得单独拿出来好好讲讲。这部分代码（`pm_fsm_state_self_test_bootstrap`和`pm_fsm_state_self_test_power_stage`）体现的是一种**极其严谨的硬件防御思维**。

很多电机炸机、烧管子，其实不是控制算法写得不好，而是硬件本身有隐患（比如自举电容干了、MOS管栅极虚焊了、采样电阻变质了）。这套代码试图在“大电流干活”之前，用微小的代价把这些隐患全揪出来。

### 5.1 自举电容体检：`pm_fsm_state_self_test_bootstrap`

**背景知识：**

绝大多数电机驱动器（比如 IPM 模块或 Gate Driver 芯片）的上桥臂 MOS 管，是靠自举电容（Bootstrap Capacitor）供电的。

-   这个电容只有在**下管导通**的时候，才能从 15V 电源充电。
    
-   如果电容没电，上管就打不开，或者打开一半（进入线性区），瞬间发热爆炸。

### 5.3 为什么说这是“艺术”？

1.  **安全性极高**：这些测试都是在**极短时间**（`tm_transient_fast`，2毫秒）内完成的。即使电路真的有短路，因为导通时间极短，电感会限制电流上升，通常不会立刻炸管子（除非已经是直通短路）。这叫**脉冲式探伤**。
    
2.  **不依赖电流传感器**：注意看，`power_stage` 测试主要靠的是**电压反馈** (`fb_uA/B/C`)。这意味着即使电流传感器坏了，它也能测出 MOS 管的好坏。
    
3.  **定量诊断**：
    

-   自举测试不仅告诉你“好/坏”，还能通过 `BST` 数组告诉你电容的**保持时间**。
    
-   功率级测试不仅告诉你“坏了”，通过分析 `IST` 数组的位模式，还能具体定位到**是哪一个管子**坏了（虽然代码里只报了一个笼统错误，但数据都在 `self_IST` 里，调试时一看便知）。

## 四、为什么FSM是辨识这类任务的“天作之合”？

1.  **时序的保证**: 辨识任务天生就是**多步骤、有先后顺序**的。FSM用`state`和`phase`完美地描述了这种时序关系。
    
2.  **非阻塞执行**: FSM的每个`case`或`phase`都只执行一小部分工作，然后立即返回。它不会像一个`while(1)`循环那样“霸占”CPU。这保证了即使在辨识过程中，主循环的其他任务（如通信、保护监控）也能正常运行。
    
3.  **状态的可追溯性**: 当辨识失败时，我们只需要打印出`pm->fsm_state`和`pm->fsm_phase`，就能立刻知道它“死”在了哪个任务的哪个步骤。这对于调试来说是无价之宝。
    
4.  **可扩展性**: 如果你想增加一个新的辨识任务，比如“辨识转矩脉动”，你只需要：
    

-   在`PM_STATE`枚举里加一个`PM_STATE_PROBE_TORQUE_RIPPLE`。
    
-   写一个新的函数`pm_fsm_state_probe_torque_ripple(pm)`。
    
-   在`pm_FSM`的两个`switch`里加上对应的`case`。
    
-   整个架构不需要做任何大的改动。
    

## 五、本讲落地：把FSM思想融入我们的开发文化

今天我们学习了代码A的FSM架构。对各位同仁有何益处呢？

### 1\. 对算法工程师

-   **告别“标志位编程”**: 以后再写任何超过两步的、有顺序的异步任务时，优先考虑用状态机来实现，而不是用一堆全局标志位和复杂的`if-else`。
    
-   **任务分解**: 在设计一个辨识算法时，先不要一头扎进公式。先用“phase 0, 1, 2, 3...”把它分解成几个独立的、可执行的步骤。
    

### 2\. 对硬件工程师

-   **理解软件的“节拍”**: 你们要意识到，软件不是随时都能响应你选的MCU中硬件中断或信号变化的。它可能正处于某个辨识`state`的`phase`中，需要执行完当前步骤才能响应。这有助于你们在MCU选型时，特别是需要考虑中断优先级和硬件握手协议时，与软件同事更好地配合。
    

### 3\. 对测试工程师

-   **测试用例要覆盖状态转移**: 你们的测试用例，不仅要测“辨识结果准不准”，还要测“状态机在各种异常情况下会不会卡死或跳错”。
    

-   例如：在`PM_STATE_PROBE_CONST_RESISTANCE`执行到一半时，突然给一个`PM_STATE_HALT`请求，看系统是否能平滑地进入停机状态。
    
-   又如：在辨识时拔掉一路相线，看系统能否正确检测到错误并进入`HALT`，而不是卡在某个`phase`里。
    

## 六、本文小结：

各位同仁，今天我们一起欣赏了状态机这首“结构之诗”，理解了它是如何为我们复杂的辨识任务带来秩序和健壮性的。

我们已经知道，代码A的辨识流程，第一步不是去测电机，而是**校准我们自己的“尺子”**。

它首先要做的是`**PM_STATE_ZERO_DRIFT**`（零点漂移校准），然后是`**PM_STATE_ADJUST_ON_PCB_VOLTAGE/CURRENT**`（电压电流标定）。

那么，我们下一讲要解决的问题就是：

**“都说要校准，到底怎么校？**
