各位同仁，我们今天文章开头的案例，来源于一个让算法工程师非常“分裂”的场景。

## 一、“我的辨识，时灵时不灵”

算法工程师小周，设计了一套基于主循环的参数辨识流程，和我们[上一讲](https://mp.weixin.qq.com/s?__biz=MzE5MTYzNjgzOA==&mid=2247485189&idx=1&sn=e25217ae4926e585d65f49a8c3bb81fa&scene=21#wechat_redirect)讨论的pm\_FSM有点类似。他在自己的电脑上用仿真软件跑，效果完美，每次结果都一样。

但当他把代码下载到真实的控制器硬件上时，怪事发生了：

1.  **结果随机**: 同样一台电机，同样的上电顺序，第一次辨识出的电感是1.1mH，第二次是1.3mH，第三次直接报错。
    
2.  **依赖“运气”**: 他发现，如果他在辨识开始前，手动转一下电机轴到某个特定角度，辨识的成功率就特别高。但如果停在另一个角度，就很容易失败。
    

小周百思不得其解：我的算法逻辑是确定的，为什么执行结果却像“掷骰子”一样随机？

**问题出在哪里？**

问题出在**软件执行与硬件事件的“脱节”**。小周的辨识代码跑在主循环（比如一个1ms的后台任务）里，而硬件事件——比如PWM周期的开始、ADC采样的完成——是发生在微秒（us）级别的、由硬件定时器精确触发的中断里。

主循环里的代码，就像一个随性的“散步者”，它什么时候执行到辨识那一步，相对于硬件的“脉搏”（PWM周期），是**不确定**的。今天它可能在PWM周期的开头拿到了采样数据，明天可能在周期末尾才拿到。这种时序上的“抖动”，对于需要精确V\*dt/di计算的参数辨识来说，是致命的。

**问题的答案在哪儿？**

就在我们今天要深入剖析的**代码B** (MotorPmsmParEst.c) 的核心架构里。

代码B的作者，选择了一条与代码A完全不同的路。他没有把辨识的主体放在一个慢悠悠的主循环状态机里，而是把它直接“塞”进了**最快、最准时**的地方——**ADC转换完成中断服务程序（ISR）**。

今天，我们就来逐行拆解 ADCEndIsrTune\_POLSE\_POS() 这个函数，看看代码B是如何利用硬件中断这个“鼓点”，来指挥辨识流程，确保每一个动作都精准地“卡在节拍上”。

## 二、中断驱动的辨识：把“大脑”安在“心脏”旁边

### 1\. 为什么是ADC中断？

-   **最准时的“闹钟”**: ADC的采样触发，通常由PWM定时器的特定事件（如计数器归零或达到峰值）来精确同步。因此，ADC转换完成中断，是整个控制系统里**最准时、抖动最小**的软件执行点。它就像心脏的每一次搏动，规律而可靠。
    
-   **最新鲜的“食材”**: ADC中断发生时，意味着最新的电流、电压采样值刚刚准备好。在中断里立刻处理这些数据，可以最大程度地减少测量延迟。
    

### 2\. 代码B的“中断+主循环”协作模式

代码B并没有把所有逻辑都塞进中断。它采用了一种**“中断里干快活儿，主循环里干慢活儿”**的协作模式。

**代码实现 (**`**MotorPmsmParEst.c**`**)**:

-   主循环任务: `SynTuneInitPos()`：这个函数由一个更大的状态机 `STATUS_GET_PAR` 调用，它负责**流程控制**，比如切换子步骤 `gGetParVarable.IdSubStep`，设置辨识标志 `gIPMInitPos.Step = 1`。它就像一个“导演”，喊“开始”和“停”。
    
-   中断服务程序: `ADCEndIsrTune_POLSE_POS()`：这个函数被注册为ADC中断的处理函数。它负责**具体执行**，比如调用 `SynInitPosDetect()` 来发波、采样、计算。它就像“演员”，负责完成导演指定的动作。
    

**二者是如何协作的呢？**

1\. 主循环的 SynTuneInitPos() 在 case 1 中，把ADC中断的处理函数设置为 ADCEndIsrTune\_POLSE\_POS：

```
SetADCEndIsr(ADCEndIsrTune_POLSE_POS);
```

2\. 然后，它在 case 2 中，把辨识启动标志位置位：

```
gIPMInitPos.Step = 1;
```

3\. 之后，主循环就进入了“等待”状态，在 case 3 里不断检查 gIPMInitPos.Step 是否变回0。

4\. 与此同时，ADC中断一次次地发生。ADCEndIsrTune\_POLSE\_POS() 每次被调用，都会检查 gIPMInitPos.Step。一旦发现它为1，就调用 SynInitPosDetect() 去执行一小步辨识任务。

5. SynInitPosDetect() 内部用自己的 step（gIPMInitPos.Step）和 PeriodCnt、Section 来管理辨识的子流程。当所有步骤都完成后，它会把 gIPMInitPos.Step 清零。

6\. 主循环的 SynTuneInitPos() 发现 gIPMInitPos.Step 变回0，就知道中断里的任务完成了，于是继续执行后续的 case 4, case 5...

你看，代码B的架构，就像一个“**导演+演员**”的剧组。主循环是“导演”，负责安排场次、切换场景。ADC中断是“演员”，负责在导演的指令下，精准地完成每一个镜头（发波、采样、计算）。这种分工，既保证了执行的**时序精确性**（演员卡点），又保证了流程的**逻辑清晰性**（导演控场）。

## 三、`ADCEndIsrTune_POLSE_POS()` 逐行走读：中断里的“快活儿”

现在我们来看“演员”到底在中断里干了些什么。也就是MotorPmsmParEst.c文件中的 ADCEndIsrTune\_POLSE\_POS 函数

```
void ADCEndIsrTune_POLSE_POS(void)
```

这个函数在中断里做的“快活儿”是：

1.  **安全与基础数据**: 中断一进来，第一件事就是检查过压，然后采集母线电压和电流。这是所有后续计算的基础。
    
2.  **时序同步**: if(EPwm1Regs.TBSTS.bit.CTRDIR == 0) 这个判断非常关键。它利用了中心对齐PWM模式下，定时器计数器会“先增后减”的特性。
    

-   CTRDIR == 1 是增计数阶段（周期的前半段）。
    
-   CTRDIR == 0 是减计数阶段（周期的后半段）。
    
-   代码选择在**减计数**阶段执行 SynInitPosDetect()，这通常是为了确保在PWM脉冲的**中心**位置附近执行计算，此时电流纹波较小，采样值更接近平均值。
    

4.  **数据缓存**: 在增计数阶段，代码把ADC采到的电流值，从全局的gIUVWQ24结构体中，复制到辨识专用的gIPMInitPos结构体里。
    
    为什么要做这个“复制”动作？
    
    这是一种数据快照（Snapshot）的思想。它确保了在减计数阶段SynInitPosDetect()函数进行复杂计算时，它所使用的电流数据，是这个PWM周期前半段采集到的、固定不变的“快照”，而不会被下一次中断的新采样值所覆盖或干扰。
    

ADCEndIsrTune\_POLSE\_POS 的设计，体现了嵌入式实时系统编程的两个核心原则：

1.  **时序同步**: 把关键计算和PWM周期绑定，确保每次都在“对的时间”做“对的事”。
    
2.  **数据一致性**: 通过“快照”机制，保证在一个计算周期内，所有输入数据都来自同一个时间点，避免了数据竞争和不一致。
    

## 四、对比代码A：两种不同的“节拍器”

现在，我们可以回头对比一下代码A和代码B在处理时序上的不同哲学。

-   **代码A的节拍器**: 是**软件FSM**。它的节拍是“**逻辑节拍**”，由fsm\_phase的切换来驱动。每个phase可以执行一个或多个PWM周期。它的优点是灵活，逻辑清晰，与硬件解耦。缺点是响应速度受限于主循环的调用频率，时序精度相对较低。
    
-   **代码B的节拍器**: 是**硬件中断**。它的节拍是“**物理节拍**”，由PWM定时器严格触发。每个节拍就是一个PWM周期。它的优点是时序精准、实时性强。缺点是代码逻辑被分散在中断和主循环中，阅读和维护更复杂，且中断服务程序必须极度高效，不能做耗时操作。
    

到这里，也许有同仁会较真儿，**哪个更好？**

答案是：**没有绝对的好坏，只有适不适合。**

-   对于代码A这种追求**模型化、可移植性、复杂算法（如Kalman）的框架**，FSM更合适，因为它能更好地组织复杂的逻辑和计算。
    
-   对于代码B这种追求**极致效率、与硬件紧密配合、完成特定整定任务的场景**，中断驱动更合适，因为它能榨干硬件的每一分性能。
    

## 五、本讲落地：给两类工程师的行动指南

### 1\. 对算法工程师

-   **尊重时序:** 在写任何与实时数据相关的代码时，都要问自己：“我的输入数据，是哪个时刻的？我的计算结果，将在哪个时刻生效？”
    
-   **区分“快活儿”和“慢活儿”**: 学习代码B的思路，把那些必须在PWM周期内完成的“快活儿”（如PI计算、坐标变换）放在中断里；把那些可以跨周期完成的“慢活”（如参数辨识的流程切换、日志记录、与上位机通信）放在主循环里。
    
-   **用示波器验证时序**: 当遇到难以复现的“玄学”问题时，不要只看软件变量。用示波器，把关键的软件IO翻转信号（比如在`ADCEndIsrTune_POLSE_POS`开头和结尾各翻转一次IO口），和硬件的PWM信号、电流采样信号放在一起看。时序上的问题，往往在示波器上一目了然。
    

### 2\. 对硬件工程师

**记得一定要提供“节拍信号”**: 各位设计的硬件，尤其是MCU的型号，要能给软件提供清晰、可靠的同步信号。PWM定时器的“零点匹配”、“周期匹配”中断，ADC的“转换完成”中断，都是算法工程师赖以生存的“节拍器”。
