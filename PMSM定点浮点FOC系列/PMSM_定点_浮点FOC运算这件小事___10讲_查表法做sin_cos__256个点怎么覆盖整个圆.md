上一篇我们用一万组数据验证了Clark变换的定点精度——最大误差不到0.3个LSB，几乎触及16位整数的理论极限。今天我们暂时跳出FOC主流程，专门看一个底层工具：**在没有FPU的芯片上，sin和cos是怎么算出来的**。

浮点版代码里，一行`arm_sin_f32(theta)`就完事。定点版里，是两个看起来名字很吓人的函数——`plook_u32u16u32n16_even6c_gf`和`intrp1d_s16s32s32u32u32n16l_f`。这俩函数一个管找表位置、一个管插值，合起来就是"查表法"的完整实现。拆开它们之前，我们先说件往事。

* * *

## 爷爷辈当年算sin(35°)是怎么算的

如果各位同仁跟爷爷辈的工程师聊起，他们会告诉你一个细节：在电子计算工具普及之前，计算sin和cos是要**翻书**的。

每个工程师、水手、天文学家的书架上，都会有一本厚厚的"三角函数表"。书里密密麻麻地列着每个角度对应的sin、cos、tan值，精度到小数点后四位或五位。要算sin(35°)？翻到35°那一页，照抄数字。

那问题来了：表里只列到整数角度，想算sin(35.5°)怎么办？

靠**线性插值**。查到sin(35°)=0.5736，sin(36°)=0.5878，35.5°在两者正中间，于是 sin(35.5°) ≈ (0.5736 + 0.5878)/2 = 0.5807。真实值是0.580703，误差不到万分之一。这种"查表+插值"的操作，当时的工程师一天要做几十上百次，熟练得跟呼吸一样自然。

大学的《数值分析》课本里讲"用直线近似曲线"的时候，可能是个有点抽象的定理。但在工程师的工具包里，这就是每天吃饭的家伙。

各位同仁现在看到的`plook`和`intrp1d`这两个函数，做的就是同一件事——**把爷爷辈工程师的手工操作，搬进C代码自动化执行。** 原理一模一样：先查表找最近的整数角度，再按小数部分做线性插值。换了个舞台而已，节目还是那个节目。

## 定点sin表的设计：256段覆盖90°

先说说表本身怎么设计。几个关键决策摆在Embedded Coder面前：

-   **问题一：存多大的范围？** 一圈360°全存？太浪费。利用sin和cos的对称性，只存**0°到90°**一个象限就够了，其他象限靠"镜像加符号"推出来。这部分逻辑与我们下一篇文章要聊的Park变换里做的象限折叠思路类似，这里先不展开。光这个决策就节省了3/4的ROM空间。
    
-   **问题二：存多少个点？** 每0.1°存一个点要900个点，太多；每10°存一个点只有9个点，精度太差。最终的选择是**256个点**——听起来是个奇怪的数字，但背后有道理。
    
-   **问题三：怎么组织输入格式？** 输入的0°~90°范围，映射到一个uint16值u=\[0, 16384\]。256个分段平均分这个范围，每段宽度 **16384 ÷ 256 = 64**。
    

这里藏着第一个精巧的设计：**16384、256、64都是2的幂**。意味着后面从输入u找表项时，"除以64"可以写成`>> 6`，"对64取模"可以写成`& 63`——都是整数运算里最便宜的操作，通常一个时钟周期就搞定。如果当年的表设计选了250个分段、每段65.5——那整除和取模都得用真的除法指令，在Cortex-M3上慢10倍不止。

定点代码里这种"专门把尺寸凑成2的幂"的小设计随处可见。看到任何写成2的幂的常数（256、64、16384、32768……），先不要把它当成普通数字，往往背后都藏着一个"让移位取代乘除"的考虑。

* * *

## plook函数：找到表的正确行

```
uint32_T plook_u32u16u32n16_even6c_gf(uint16_T u, uint16_T bp0, uint32_T
```

剥开一堆类型转换，核心就两行：

```
bpIndex = u >> 6;              // 整数索引：u落在哪个分段里
```

翻译回爷爷的三角函数表：**bpIndex就是"翻到哪一页"，fraction就是"在本页和下一页之间的位置百分比"**。

为什么`(u & 63)`还要再`<< 10`一次？因为这个小数部分要交给插值函数用。原始的"&63"结果范围只有\[0, 63\]，6位精度。左移10位之后变成\[0, 64512\]，等于扩展到Q16小数格式——插值乘法的精度能提到16位。这一步基本没有成本，但让最后的插值结果精度大幅提升。

边界处理也值得一提：如果u正好等于16384（即90°边界），`u >> 6`会得到256，超出表的最大索引255，代码直接钳到`maxIndex - 1 = 255`，fraction设为满量程65536——等于强制拿最后一个分段的右端点做插值，结果就是sin(90°)=1.0。这种"边界饱和"处理浮点版根本不用操心，定点版每次都得显式地写。

## intrp1d函数：两点之间走直线

```
int16_T intrp1d_s16s32s32u32u32n16l_f(uint32_T bpIndex, uint32_T frac,
```

以上代码，在数学上其实就是一行：

![](https://mmbiz.qpic.cn/sz_mmbiz_png/vvmIAIMZsARVEjN161TicbT2VJJOouFZbqiau4BhBgU715RibrVy5zfYpyDPmW7GjUutTAq4Y323I2HMX9t4qtct6BkwLib8fmc5ibHPedu11CIg/640?wx_fmt=png&from=appmsg)

定点版本把小数frac写成Q16格式（就是上一步左移10位得到的那个东西），所以乘完之后要`>> 16`把格式搬回来——这是[第4篇](https://mp.weixin.qq.com/s?__biz=MzE5MTYzNjgzOA==&mid=2247486177&idx=1&sn=948819bb60e37f1186a91480aab0232a&scene=21#wechat_redirect)讲过的Q格式运算基本规则。

注意`(table[bpIndex + 1] - yL_0d0) * frac` 这一步。两个Q15值相减得到一个范围在\[-32768, 32767\]的int16（相邻两个表项的差），再乘一个Q16的小数。乘法结果能有多大？相邻表项的差最多不会超过两个相邻角度的sin值差，对于0.35°的分段宽度来说，最大差值出现在0°附近（此处sin函数斜率最大），Q15下差值约200左右。乘完之后int32完全装得下，不用担心中间结果溢出。

## 精度验算：sin(45.5°)

拿一个具体例子跑一遍。目标：用这套查表法算sin(45.5°)，看和真实值差多少。

**输入转换**：角度45.5° → u = 45.5/90 × 16384 = **8283**

**plook执行**：

-   `bpIndex = 8283 >> 6 = 129`（对应表项角度 = 129×90/256 = 45.3516°）
    
-   `remainder = 8283 & 63 = 27`
    
-   `fraction = 27 << 10 = 27648`（小数部分 = 27648/65536 = 0.4219）
    

**表项查询**：

-   `table[129]` = Q15(sin(45.3516°)) = **23312**
    
-   `table[130]` = Q15(sin(45.7031°)) = **23453**
    

**intrp1d执行**：

-   差值 = 23453 − 23312 = 141
    
-   插值增量 = (141 × 27648) >> 16 = 59
    
-   输出 = 23312 + 59 = **23371**
    

**对账**：真实sin(45.5°) = 0.71325 × 32768 = **23372**。误差 **1个LSB**，相对误差0.004%。

再用10000组随机角度做一次全面测试，结果是：平均误差0.71 LSB，**最大误差3 LSB**，90.4%的样本误差不超过1 LSB。换句话说——**这套查表法已经贴着16位整数的精度天花板在走了。**

作为对比，如果偷懒把插值去掉、只取最近的表项（nearest neighbor），最大误差会涨到**102 LSB**——是带插值版本的34倍。那一步看起来简单的线性插值，终究是值得的。

## 精度vs存储：256这个数字怎么来的

有同仁可能会问：如果把分段加到512，误差是不是就能再降一半了？

是的，而且不止一半。把表从256段改成512段，每段角度从0.35°变成0.18°，插值误差可以再降大约**4倍**（理论上，因为线性插值的最大误差和分段宽度的平方成正比）。单代价是表格从514字节涨到1026字节——多占半个KB的ROM。

Embedded Coder选256，是在"精度够用"和"存储省钱"之间找的平衡点。对FOC电流环这种应用，3 LSB的插值误差相对于ADC本身的采样噪声（12位ADC约0.024%）和电机模型的建模误差来说，已经小到可以忽略。再加精度，边际收益不大，还得付出ROM代价，不划算。

这种权衡非常典型——定点开发的很多决策都是这样的平衡，没有绝对的最优解，只有对当前应用最合适的选择。换一个场景（比如高端伺服、超声波测距、正弦波发生器），可能就会选512甚至1024分段了。

## 一个有意思的对照

说了半天定点的查表法，回头看浮点版的`arm_sin_f32()`——它的内部实现其实也是查表加多项式逼近，只是表的组织形式、插值的阶数（CMSIS用的是三次多项式而不是线性插值）和定点版不同。**查表+插值这条路线，不管你用定点还是浮点，本质上都绕不开。** 区别只在于谁来写那些移位和边界判断——定点版靠Embedded Coder或软件工程师手写，浮点版由CMSIS库封装掉了。

这也是我想通过这个系列给各位同仁传递的一个底层观察：浮点并不比定点"更高级"，只是把很多苦差事藏在了FPU硬件和库函数里。当你看到定点代码里那些绕来绕去的位操作时，别觉得它"落后"——它只是把那些平时看不见的工作，全部摊开在你面前了。

## 本文小结

各位同仁，查表法的本质是把爷爷辈工程师翻三角函数表加手工插值的操作，搬到C代码里自动化执行。FOC定点代码里用256个采样点覆盖0°~90°，配合象限折叠就覆盖了整个360°。`plook`函数用`>> 6`和`& 63`找到表项索引和小数部分——分段数选256是为了让这两个操作都变成最便宜的移位和位与，背后藏着"把尺寸凑成2的幂以规避除法"的标准套路。`intrp1d`函数做一次定点线性插值，乘法的Q16小数格式让插值精度接近理论极限。10000组随机角度测试下来，最大误差3 LSB，90%的情况只差1 LSB——这套方法已经把16位整数的精度榨到了尽头。表大小514字节，精度和存储在这里达到了平衡。
